# Auto-tune performance

Deliver a verified improvement to the user's workload, or a useful diagnosis explaining why no candidate earned acceptance. Run the tuning loop autonomously within the requested scope and budget. A tuning request authorizes relevant local diagnosis, reversible edits and validation; an analysis-only request remains read-only. Keep production rollout, paid capacity and private-data transfers within existing authorization.

Inspired by [Give Your Agent a Profiler](https://danlevy.net/performance-tuning-with-an-agent/). Measure outcomes, inspect where resources go, and verify the work actually happened. Neither familiar optimization advice nor a large profile frame establishes a cause.

## Establish the contract

Read project instructions, the current worktree and the relevant runtime/build/benchmark paths. First look for the previous performance plan and project preferences. “Check performance again” normally reruns the most recent matching exercise with the same workload/gates; refresh source, environment, baseline and authorization rather than redesigning the exercise or reusing stale results. Preserve unrelated edits and existing behavior. Identify the user-visible operation, workload sizes and important slices, the desired latency/throughput/resource objective, acceptable tradeoffs, and hardware/runtime/environment. Do not replace a slow operation with less work, weaker durability, different output, worse quality or removed design/accessibility to win a timing.

Use the project's performance record or create `performance/<task>/plan.md` from [the contract template](assets/plan-template.md). Put raw measurements, traces and logs in its configured artifact directory, or a named ignored directory when they are bulky/private; the reviewed plan must point to them. Record commands, source/dirty-patch identity, fixtures, environment, instruments and hypothesis for every experiment. Read [measurement design](references/measurement.md) when defining or reviewing a harness.

Freeze acceptance criteria before testing candidates: primary objective and minimum worthwhile gain; per-slice regression limits; correctness/product/resource gates; observation units and uncertainty method; screening/confirmation schedule; time, experiment and spend bounds. Infer reasonable provisional bounds from the task and record them; ask only when an unresolved tradeoff would change the product or spending. A small improvement needs a proportionate experiment, not an elaborate performance program.

Read [search strategy and project preferences](references/strategy.md) to select tuning parameters, persist priorities, consider a minimal starting point and choose scaling/architecture alternatives. Store confirmed preferences and rerun recipes in the target project, never in the global skill or another project's memory. When priorities are unclear or the user seems frustrated by the time/cost/results, name the tradeoff and ask a concise question while continuing independent diagnosis. Do not repeatedly ask settled preferences or treat frustration as permission to break requirements.

## Prove the instrument before optimizing

Reproduce the symptom on the actual execution path and record an unmodified baseline. Use production/optimized builds and explicit cold/warm scenarios where relevant. Prove workload completion and outputs with behavioral oracles: requests served, records committed, scroll destinations reached, expected pixels/selection/keyboard behavior, or model outputs satisfying the quality gate. Check errors, drops, timeouts, cancellation and fallback paths alongside latency. A failing or skipped workload is not a fast sample.

Identify the noise floor with repeated independent runs. Verify actual device/renderer, runtime, throttling, cache, source and background load; requested settings alone are not evidence. If the baseline is unstable, the harness invalid or the tools unavailable, repair or narrow the instrument first. Do not silently substitute a machine or loosen host-wide profiler protections. Distinguish a reproducible environment blocker from product performance.

## Locate the limiting resource

Start with coarse outcome/resource signals to locate the expensive phase, then choose a layer/platform-specific instrument that distinguishes the live hypotheses. Read only the relevant sections in [instruments](references/instruments.md); for queues, APIs, GPU and LLM services also read [serving and capacity](references/serving.md). If useful tooling or access is missing, actively arrange it: explain the question it answers, why current signals cannot answer it, destination/scope, overhead/cost and fallback. Install/use trusted tooling when already authorized; request only missing permission for consequential access, privileges, uploads or paid work. Do not stop at “no profiler installed,” install every tool, or silently weaken the measurement.

For web targets, read [web performance](references/web-performance.md): run a small frame-pacing/blocking and visual pass with representative scrolling, keyboard input and navigation; aim for 60 FPS or the appropriate higher-refresh budget and verify the actual renderer. Obtain low-level browser evidence through available DevTools/CDP tooling. Drill into load audits, payloads, JS/CSS coverage, bundles or CDN delivery only when the symptom or request warrants it.

Map end-to-end time into phases and dependencies. Ask whether the operation is executing, waiting, transferring, allocating/collecting, decoding/rendering, or feeding an accelerator. Inspect self versus inclusive cost, wall versus CPU time, queue versus service time and off-thread work. Correlate the profile with the slow interval. Verify causal influence with a bounded intervention; a hot stack, high utilization or correlated trace event is a lead, not proof.

Estimate leverage before editing. For a serial fraction `f` sped up by `s`, the ideal end-to-end speedup is bounded by `1 / ((1-f) + f/s)` under that model. Queueing, overlap and bottleneck migration require a new model. Prefer removing unnecessary repeated work or data movement before making each repetition faster. Preserve required work and account for cold-start, memory, downstream load and ongoing maintenance.

## Run a bounded experiment loop

1. Rank a small hypothesis queue by evidence, reachable user benefit, implementation/risk and experiment cost. **By default consider and record a minimal/bare-bones or clean-rebuild arm**, including why it is useful or inapplicable. For complex stacks/prompts, estimate the load-bearing pieces, subtract or rebuild in an isolated experimental path, and add necessary pieces back with correctness/quality and performance checks at each step. Preserve the original; “start over” is a testable alternative, not permission to erase the project or required behavior. For each candidate record mechanism, predicted metric **and trace** movement, disconfirming observation, tradeoffs and rollback.
2. Change one coherent mechanism. Isolate the treatment with a flag or separate source/build identity. Tune coupled parameters as a named bundle only when their interaction is the hypothesis; attribute the result to that bundle. Keep benchmark fixtures, oracles and thresholds unchanged between arms.
3. Screen cheaply on representative development workloads. Run correctness first and measure outcomes with diagnostic tracing off. Interleave baseline/candidate or randomize balanced paired blocks with appropriate resets. Preserve raw runs and failures; do not delete inconvenient outliers or compare warm candidate against cold baseline.
4. Reject correctness failures and material guardrail regressions even if the headline improves. Treat an uncertain result as uncertain. Prefer the simpler baseline when no meaningful gain is supported. Revert only owned candidate edits; keep the evidence and rejected hypothesis.
5. For a promising candidate, freeze it and confirm on fresh preplanned runs and important untouched workloads/sizes/environments. Include a reversion/ablation check when needed to test causality. Do not repeatedly inspect confirmation results and keep adding samples until they pass. Read [decisions and evidence](references/decisions.md) for acceptance and the optional paired-comparison helper. Choose an installed Node 20+ or Python 3.10+ runtime, or its Bash 3.2+ dispatcher; record and retain the interpreter through the experiment. A validation failure must not trigger runtime fallback.
6. Re-profile the accepted build briefly to check the predicted mechanism and locate the new bottleneck. Measure the final combined patch again: independently good changes can interfere. Continue only while remaining hypotheses can plausibly meet the objective within the budget. Match vertical tuning or horizontal partitioning/fleets to the workload's critical path, reliability and cost requirements; use an available `remote-compute` skill for authorized capacity when appropriate. If meaningful gains stall or the target is structurally out of reach, present quantified architectural/requirement alternatives from the strategy reference. Do not launch a breaking redesign by default.

Tell the user what the evidence changes: dominant cost, invalid instrument, rejected tradeoff, confirmed gain, new bottleneck or budget limit. Update after the baseline, first diagnostic, each meaningful candidate decision and at long-running checkpoints. Report costs and bounded forecasts when experiments use paid services. Existing remote compute workflows can supply capacity; this skill neither requires them nor assumes their permissions.

## Finish with a defensible decision

Stop when the objective is confirmed, no worthwhile hypothesis remains, the experiment budget is exhausted, or a concrete external blocker prevents valid work. Leave the best **confirmed** candidate integrated and tested, or restore the owned baseline edits. Do not ship an unconfirmed last experiment because time ran out.

Report the affected workload/environment; before/after values and units; absolute and relative effects with spread/uncertainty; independent run counts; correctness/product/resource gates; accepted/rejected changes; artifact paths and rerun command; residual bottleneck and unmeasured cases. Label screening, microbenchmark, traced diagnostics and production validation distinctly. A local improvement is not a fleet/SLO claim. Add a meaningful regression check at the stable behavioral seam; avoid noisy timing thresholds in ordinary unit tests. If rollout is authorized, canary with abort/rollback criteria and verify real traffic; otherwise leave the change reviewable.

For every target, use the [concise evidence summary](references/decisions.md#concise-findings-for-every-target): lead with outcome and next action, list what was checked, distinguish proved findings from supported suspicions, name unmeasured/blocked conditions and any specific user help needed. Include successful/no-change outcomes; do not hide missing evidence in a long tool transcript.
